*Part 9 of 16 in a series on [specforge](https://github.com/ashitpatel/specforge). The previous posts showed verdicts. This one shows the step that decides what earns a verdict at all — and where it can go wrong. No new evidence here; the exhibits are the earlier posts'.*

*Level L2 · Needs: part 2. Ranking, miss modes, the checklist.*

Every bug this series caught was caught inside a *slice*: one behavior, the state it owns, the property at risk. The kombu limit race was the `_dirty` slice. The stomp wake-up was the send/notify slice. The pool's waiter fairness was the waiter-queue slice. Nothing was ever modeled whole. That choice — what gets modeled, and what it's checked against — is the most consequential judgment in the tool. This post puts it on the table: why slices, how they're ranked, how ranking misses, and how you watch for the gaps.

## The compromise

Three obvious scopings, each broken a different way:

- **One spec for the project** drowns. State spaces multiply across behaviors, the model becomes unreadable, and the checkers time out. This is the heavyweight failure the 1998 survey predicted.
- **One spec per function** cuts where the bug lives. Temporal bugs sit *between* functions — the check in `_add_when_empty`, the act in `acquire`, forty lines apart. Function boundaries slice through the very window that matters.
- **One spec per module** follows files instead of risk. One module can hold three unrelated state clusters; one race can span two modules. Code layout is about ownership and readability, not about where interleavings break.

A slice follows the risk shape instead: the state cluster, its writers, and the property, wherever the files put them. Small enough to exhaust, shaped like the bug. In greenfield runs the cut comes from the requirements (one feature = one coherent behavior plus the data it owns, approved by the user); in from-code runs it comes from observed sharing (state, lock shapes, writers). Either way the rule is the same: model the cluster, not the container.

## How slices are ranked

From-code runs can propose hundreds of candidates; a budget covers a handful. Ranking is `score = (E + B) × H × P`, in plain words:

- **E, evidence**: race candidates with their locksets and switch windows, plus static bug patterns (check-then-act, wait without re-check). Diminishing returns apply — ten races on one item are not ten times the evidence.
- **B, bonus**: a small nudge for docstring and comment claims, treated as hints to test rather than facts.
- **H, history**: churn and fix-like commits on the involved functions — code that broke before is likelier to break again — capped so history can never fully bury quiet code.
- **P, prior**: a weak structural prior from the census. Deliberately the smallest term.

The agent then chooses from the ranked list under a recorded bar: every proposal ranked above its lowest pick must be chosen or skipped *with a written reason*. Skips are data, not silence — "handler closes both files on reading" is a judgment the record keeps.

## Three ways ranking misses

Documented, with numbers, because a series about falsification doesn't get to hide these:

1. **The screen cliff.** Runs propose hundreds; the screen reads dozens. In one run the first hits on real bugs sat at ranks 49–166 — below any reasonable screen line. Raising the screen helps until the budget runs out; the cliff is structural, and the honest response is the `owed` list: named debt to the next sweep, not a gap nobody recorded.
2. **Demotion burying.** Scores get demoted for uncertainty (a caller-only pattern, a GIL-unreachable window), and demotion compounds: a 0.25 floor factor moved one real bug from rank 2 to rank 16 in a recorded case. The demotions are principled — uncertain evidence *should* weigh less — but the record shows them burying real bugs anyway.
3. **Tuning circularity.** The engine has been tuned on the same projects it gets measured on (Log4j not least). A rank earned after tuning partly measures the tuning. The defense is the one part 4 stated: trust the *flagging* (a touched function writes the state — old, stable mechanism), discount the exact *ranks*.

## Why you review every candidate

Because the tool's misses have the same shape as its hits: a slice is a hypothesis about where risk lives, and ranking is a bet about which hypotheses pay. The bar exists to force the bet into the open — no silent passing-over — but an open bet can still be wrong. Reviewing every candidate above the line costs minutes per item — state, functions, property, one paragraph of why. The screen cliff above shows what skipping costs. The user who reviews the list is the last ranking factor, and the only one with context the tool can't see: which code is new, which is load-bearing, which scared the last person who touched it.

## The gap-watch checklist

Six things to check on any run, each with the tool that answers it:

1. **Unsliced requirements.** Functional requirements in no slice are modeled nowhere. (`design_slice_status`; blocks `forge_done` once slicing starts.)
2. **Thin slices.** One requirement alone in a slice is sometimes right, often a sign the cut followed files instead of behavior. (Same tool, flagged.)
3. **Unrefuted properties.** A property nothing has broken may be true or vacuous — the difference is a mutant or variant that violates it. (`forge_done` requires falsifiability per requirement.)
4. **Stale models.** Code the model doesn't name that writes the model's state means the model describes yesterday's code. (The review's stale-models check.)
5. **Owed debt.** Proposals below the screen line are owed to the next sweep by name. Debt is fine; unnamed debt is a gap.
6. **Composition seams.** Slices compose through pinned interfaces; an interface change with no client re-check is a hole at the seam. (The review's stop rule and client re-checks.)
